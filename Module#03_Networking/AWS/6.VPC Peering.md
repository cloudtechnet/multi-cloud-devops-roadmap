# AWS VPC Peering — End-to-End Explanation + Real-World Lab

## 1. What is AWS VPC Peering?

**VPC Peering** is a private network connection between **two VPCs**.

It allows resources in VPC-A to communicate with resources in VPC-B using **private IP addresses**, without sending traffic through the public internet.

### Simple Architecture

```text
                 AWS Region
              ap-south-1
                    |
        +-----------+-----------+
        |                       |
   VPC-A: 10.0.0.0/16     VPC-B: 172.16.0.0/16
        |                       |
   Private Subnet           Private Subnet
   10.0.1.0/24              172.16.1.0/24
        |                       |
     EC2-A                  EC2-B
   10.0.1.X              172.16.1.x
        |                       |
        +------ VPC Peering -----+
             pcx-xxxxxxxx
```

For example:

* **VPC-A:** `10.0.0.0/16`
* **VPC-B:** `172.16.0.0/16`
* EC2-A: `10.0.1.10`
* EC2-B: `172.16.1.10`

EC2-A can communicate with EC2-B using:

```text
20.0.1.10
```

# 2. Real-World Example

Imagine an organization has two applications.

### VPC-A — Application VPC

```text
10.0.0.0/16

Frontend
   |
Backend
   |
Database
```

### VPC-B — Shared Services VPC

```text
20.0.0.0/16

Monitoring
Logging
Jenkins
Internal DNS
Security Tools
```

The company wants the application servers in VPC-A to communicate with Jenkins or monitoring servers in VPC-B.

Instead of exposing those servers to the internet, they create:

```text
VPC-A
10.0.0.0/16
     |
     | VPC Peering
     |
VPC-B
20.0.0.0/16
```

Communication stays on the AWS private network.

---

# 3. Important Concept

Creating a VPC Peering connection **alone is not enough**.

You need to configure:

```text
1. VPC-A
2. VPC-B
3. VPC Peering Connection
4. Route Table in VPC-A
5. Route Table in VPC-B
6. Security Groups
7. Network ACLs, if applicable
```

The most important point for students:

> **VPC Peering + Routes + Security Rules = Communication**

---

# 4. Important Rules

### Rule 1 — CIDR should not overlap

Good:

```text
VPC-A = 10.0.0.0/16
VPC-B = 20.0.0.0/16
```

Bad:

```text
VPC-A = 10.0.0.0/16
VPC-B = 10.0.0.0/16
```

Overlapping CIDRs prevent normal VPC peering connectivity.

---

### Rule 2 — Peering is not transitive

Suppose:

```text
VPC-A
   |
   | Peering
   |
VPC-B
   |
   | Peering
   |
VPC-C
```

This does **NOT** mean:

```text
VPC-A ---> VPC-C
```

automatically.

VPC Peering does not provide transitive routing.

# 7. Step 1 — Create VPC-A

Go to:

**AWS Console → VPC → Your VPCs → Create VPC**

Select:

```text
Resources to create:
VPC only

Name:
VPC-A

IPv4 CIDR:
10.0.0.0/16

IPv6:
No IPv6 CIDR block

Tenancy:
Default
```

Click:

**Create VPC**

You now have:

```text
VPC-A
10.0.0.0/16
```

# 13. Step 7 — Create VPC Peering Connection

Go to:

**VPC → Peering connections**

Click:

**Create peering connection**

Enter:

```text
Name:
VPC-A-to-VPC-B

Requester VPC:
VPC-A

Account:
My account

Region:
This Region

Accepter VPC:
VPC-B
```

Click:

**Create peering connection**

You will get something like:

```text
pcx-0123456789abcdef
```

This is your **VPC Peering Connection ID**.

---

# 14. Step 8 — Accept the Peering Connection

Go to:

**VPC → Peering connections**

Select:

```text
VPC-A-to-VPC-B
```

Choose:

**Actions → Accept request**

Confirm.

Status should become:

```text
Active
```

Important:

```text
Pending Acceptance
        ↓
Accepted
        ↓
Active
```

---

# 15. Step 9 — Configure Route Table in VPC-A

This is the most important step.

Go to:

**VPC → Route Tables**

Find the route table associated with:

```text
VPC-A
10.0.1.0/24
```

Go to:

**Routes → Edit routes → Add route**

Add:

```text
Destination:
20.0.0.0/16

Target:
Peering Connection

pcx-xxxxxxxx
```

So VPC-A's route table becomes:

```text
Destination       Target
--------------------------------
10.0.0.0/16       local
20.0.0.0/16       pcx-xxxxxxxx
```

Meaning:

> If traffic is going to `20.0.0.0/16`, send it through the VPC Peering connection.

---

# 16. Step 10 — Configure Route Table in VPC-B

Now configure the opposite direction.

VPC-B route table:

```text
Destination       Target
--------------------------------
20.0.0.0/16       local
10.0.0.0/16       pcx-xxxxxxxx
```

This is required because routing must work in **both directions**.

Think:

```text
EC2-A
10.0.1.10
   |
   | Destination 20.0.1.10
   ↓
VPC-A Route Table
   |
   | 20.0.0.0/16
   ↓
VPC Peering
   |
   ↓
VPC-B
   |
   ↓
EC2-B
20.0.1.10
```

Return traffic:

```text
EC2-B
20.0.1.10
   |
   ↓
VPC-B Route Table
   |
   | 10.0.0.0/16
   ↓
VPC Peering
   |
   ↓
VPC-A
   |
   ↓
EC2-A
```

---

# 17. Step 11 — Configure Security Group

Now we have routing.

But routing alone isn't enough.

The Security Group must allow the traffic.

For EC2-B's Security Group, allow traffic from VPC-A.

For example, for ICMP testing:

```text
Type:
All ICMP - IPv4

Source:
10.0.0.0/16
```

Or, for SSH:

```text
Type:
SSH

Port:
22

Source:
10.0.0.0/16
```

For an application:

```text
TCP 8080
Source:
10.0.0.0/16
```

# 18. Step 12 — Test Connectivity

Connect to EC2-A.

Run:

```bash
ip addr
```

Find the private IP.

Example:

```text
10.0.1.10
```

Now try:

```bash

```

If ICMP is allowed, you should see:

```text

64 bytes from 20.0.1.10
64 bytes from 20.0.1.10
```

Congratulations!

You have successfully configured:

```text
EC2-A
   |
   ↓
VPC-A
   |
   ↓
Route Table
   |
   ↓
VPC Peering
   |
   ↓
VPC-B
   |
   ↓
EC2-B
```

# 20. What Happens Behind the Scenes?

Suppose EC2-A sends:

```text
Source:
10.0.1.10

Destination:
20.0.1.10
```

The operating system sends the packet to the VPC networking layer.

VPC-A checks its route table:

```text
20.0.0.0/16 → pcx-xxxxxxxx
```

AWS sends the packet through the peering connection.

VPC-B receives it.

VPC-B checks its route table and allows the traffic to:

```text
20.0.1.10
```

Then EC2-B receives the packet.

# 21. Troubleshooting Lab

If this doesn't work:

```bash
ping 20.0.1.10
```

Check these **7 things**.

### 1. Peering status

Should be:

```text
Active
```

---

### 2. CIDR ranges

Make sure they don't overlap.

```text
VPC-A = 10.0.0.0/16
VPC-B = 20.0.0.0/16
```

---

### 3. VPC-A route table

Must contain:

```text
20.0.0.0/16 → pcx-xxxxxxxx
```

---

### 4. VPC-B route table

Must contain:

```text
10.0.0.0/16 → pcx-xxxxxxxx
```

---

### 5. Security Group

Make sure EC2-B allows the required traffic.

For ping:

```text
ICMP
Source:
10.0.0.0/16
```

---

### 6. Network ACL

Check NACL rules if you have customized them.

The default NACL normally allows traffic.

---

### 7. OS firewall

The Linux instance itself can also block traffic.

Check:

```bash
sudo systemctl status firewalld
```

If needed, inspect:

```bash
sudo firewall-cmd --list-all
```

# 22. VPC Peering vs Internet

### Without VPC Peering

```text
EC2-A
  |
  ↓
Internet Gateway
  |
  ↓
Internet
  |
  ↓
Internet Gateway
  |
  ↓
EC2-B
```

This isn't the normal design for private VPC-to-VPC communication.

### With VPC Peering

```text
EC2-A
  |
  ↓
VPC-A
  |
  ↓
VPC Peering
  |
  ↓
VPC-B
  |
  ↓
EC2-B
```

Private communication.

# 24. Key Points for Students

Remember this formula:

```text
VPC Peering
      +
Route Tables
      +
Security Groups
      =
Private VPC-to-VPC Communication
```

And remember:

```text
❌ Peering alone does not create connectivity

❌ Peering is not transitive

❌ Overlapping CIDRs are not supported for normal peering connectivity

✅ Both VPCs need appropriate routes

✅ Security Groups must allow the required traffic

✅ Communication uses private IP addresses
```

### Interview Question

**Q: I created VPC Peering, but EC2 instances cannot communicate. What will you check?**

A simple answer:

> First, I check whether the VPC peering connection is active. Then I verify that both VPC route tables have routes pointing to the other VPC CIDR through the peering connection. After that, I check Security Groups, NACLs, and the instance OS firewall. I also make sure the two VPC CIDRs are not overlapping.
